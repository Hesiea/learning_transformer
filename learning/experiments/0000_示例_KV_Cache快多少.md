## 1. 问题

开启 KV Cache 之后，生成结果是否与全量前向**逐 token 完全相同**？
加速比是多少，为什么加速比会随生成长度变化？

## 2. 预测（跑之前写）

| 我预测 | 理由 |
|---|---|
| 输出应当**完全相同** | K/V 只取决于历史 token、不依赖未来，缓存是数学上的等价变换 |
| 会有 1e-6 量级的数值误差 | 浮点加法顺序变了（拼接后一次性算 vs 逐步累加） |
| 长度越长加速越明显 | 无 cache 每步 O(T²)，有 cache 每步 O(T)，比值 ∝ T |

## 3. 设计

- **自变量**：`use_cache` ∈ {False, True}；生成长度 ∈ {16, 48, 63}
- **控制变量**：同一 checkpoint、同一 prompt、`temperature≈0`（贪心，消除采样随机性）
- **因变量**：逐 token 是否相同、logits 最大误差、耗时、加速倍数、token/s
- **规模**：模型 tiny（L4/H4/C128，约 0.81M 参数）、`block_size=64`、CPU 单条序列
  （长度上限取 63 = block_size−1，再长窗口就要滑动，两条路径的历史范围不再一致，
  比较会失去意义）

## 5. 对账

| 我预测 | 实际 | 差在哪 |
|---|---|---|
| 输出完全相同 | ✅ 不同位置数 = 0 | 一致 |
| 误差 1e-6 量级 | ✅ 2.384e-06 | 一致 |
| **长度越长加速越明显** | ⚠️ 16→1.05x，48→1.23x，但 63 回落到 1.17x | **这一条想错了：不是单调的** |

**预测错在哪**：我把「复杂度从 O(T²) 降到 O(T)」直接等同于「加速比单调增长」，
忽略了这是**渐近结论**，而实测处在小规模区间，有两件事在抵消它：

1. **固定开销占比高**：每步都要 `torch.cat` 拼接历史、构造掩码，
   序列短时这部分省不了，所以 T=16 时只有 1.05x。
2. **靠到 block_size 边界会触发窗口重建**：长度逼近 63 时缓存要作废重建，
   多出一次全量前向，于是 63 反而比 48 慢。

**更一般的教训**：渐近复杂度只描述「T 很大时会怎样」，
真实测量里永远有常数项和边界条件。**看到 O(·) 就用它预测小规模实测值，是会翻车的。**

## 6. 结论与新问题

- **一句话结论**：KV Cache 是严格等价的（误差仅来自浮点顺序），
  但收益随长度**先增后受边界影响**，短序列下几乎无收益。
- **适用范围**：本结论来自 block_size=64 的小模型、CPU、单条序列。
  真实部署有批处理与显存带宽因素，平衡点会移动。
- **新问题**：
  1. 如果 block_size 放大到 1024，加速比会怎么变？盈亏平衡点在哪个长度？

     T=1024、float32 时占多少？
